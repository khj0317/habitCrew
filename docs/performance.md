# HabitCrew 성능 측정 결과

- 환경: Testcontainers PostgreSQL 17 · Redis 7, 측정마다 7번 돌린 중앙값

## 1. 피드 페이지네이션: OFFSET vs 커서

한 크루에 인증 201,000건, 한 페이지 10개. `EXPLAIN ANALYZE`의 실행 시간(ms)

| 몇 번째 글부터 | OFFSET (ms) | 커서 (ms) | 차이 |
|---:|---:|---:|---:|
| 0 | 0.108 | 0.090 | 1배 |
| 1,000 | 0.600 | 0.124 | 5배 |
| 10,000 | 3.708 | 0.161 | 23배 |
| 100,000 | 29.752 | 0.108 | 275배 |
| 190,000 | 64.290 | 0.122 | 527배 |

OFFSET은 앞의 글을 모두 읽고 버리므로 뒤로 갈수록 느려지고, 커서는 인덱스 `(crew_id, id DESC)`에서 바로 그 위치로 가서 어느 페이지든 비슷하다.

## 2. 월간 랭킹: DB 집계 vs Redis Sorted Set

실제 크기의 크루(30명 × 한 달, 약 600건). 한 번 조회하는 데 걸린 평균 시간(ms, 1,000번 평균)

| 방식 | 평균 (ms) |
|---|---:|
| DB `GROUP BY` + `ORDER BY` | 0.885 |
| Redis `ZREVRANGE` | 0.815 |

이 규모에서는 둘 다 1ms 안팎이라 사용자가 느끼는 차이는 없다. Redis 랭킹은 성능보다는 대상이 커질 때(전체 사용자 랭킹 등)를 대비한 구조이고, 그때 생기는 캐시 일관성 문제를 미리 다뤄 본 데 의미가 있다.

## 3. 사진 크기

스마트폰 사진과 비슷하게 잡음을 넣은 4000×3000 JPEG(품질 95)를 서버가 처리했을 때

| 파일 | 크기 | 원본 대비 |
|---|---:|---:|
| 원본 (4000×3000) | 5.0MB | 100% |
| 크게 보기 (1600×1200) | 170KB | 3% |
| 피드 썸네일 (480px) | 5KB | 0.1% |

처리 시간(디코딩·축소·인코딩 두 번): 524 ms. 피드 10개를 볼 때 원본이라면 약 50.0MB, 썸네일은 약 51KB를 받는다.

> 주의: 측정용 사진은 그라데이션에 잡음을 넣어 만든 것이라, 줄이면 잡음이 평균되어 사라지면서 썸네일이 실제보다 훨씬 작게 나온다.
> 실제 스마트폰 사진은 디테일이 많아서 썸네일이 수십 KB 정도로 더 크다. 브라우저에서 실제로 올려 본 3000×2000 사진은 596KB → 94KB(1600px)였다.

## 다시 측정하기

```powershell
cd backend
.\gradlew.bat benchmark
```

결과는 `backend/build/benchmark/result.md`에 생긴다. 실제 PostgreSQL·Redis 컨테이너에서 재므로 Docker가 켜져 있어야 한다.
